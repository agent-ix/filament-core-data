# ADR-0011: Domain packages: construct kinds are module data

## Context

A domain package — `spec-objects-business`, `spec-objects-systems` and those
that follow — declares object types whose instances are more than records. An
aggregate root names its members, a nested entity names its one owner, a
repository names what it persists, a state machine names its transitions, and a
port names its direction and interface. The semantic IR (FR-142) must carry each
of these as a construct the backends generate and the readers check, and the
extraction frontend (FR-143) must lift each artifact to it.

Every domain package is authored and versioned outside this repository. The
business module ships at `0.7.0`, the systems module is being authored under
[agent-ix/spec-objects-systems#10](https://github.com/agent-ix/spec-objects-systems/issues/10),
and more domains are planned. The IR contract, its three readers and five
backends are released from this repository on their own cadence.

The module manifest (filament-core-service FR-035) carries, per object type, an
optional `construct` declaration: an `identity`, a `shape`, a presence for each
member, the roles each reference member admits, the rules the construct selects
and an opaque `meaning` id owned by QSpec. The roles are the object type's own
`roles`, declared in the same manifest.

This is a decision about where a construct kind is defined.

## Options

### Option A — the contract enumerates each domain's kinds

The IR schema, the readers and every backend name each domain construct kind
and its members, and each new domain kind is a contract revision.

Every domain release then waits on a contract release, and every contract
release re-opens every reader and backend. The same kind is described twice —
once in the module that owns the object type and once in the contract — and
nothing keeps the two in agreement.

### Option B — a per-domain extension contract

Each domain package publishes a schema fragment that the contract composes.

The readers still need domain-specific code to check the fragment's members,
and the backends still need domain-specific code to generate them. The fragment
moves the enumeration without removing it.

### Option C — the contract fixes a construct vocabulary; modules declare kinds in it

The contract defines a closed core vocabulary: eight core kinds, the identities
`identified`, `value` and `none`, the shapes `record`, `enumeration`,
`interface`, `state_machine`, `sequence` and `namespace`, the member names with
their presences, the reference members, and the rules each tied to the member
presence it checks. A domain kind is `{module, name}`, and its declaration is
module data, carried into each document in a `constructs` table with the
module's version and manifest digest.

## Decision

**Option C.** A construct kind outside the eight core kinds is `{module, name}`.
Its declaration is read from the owning module's manifest, checked against the
core vocabulary and the loaded modules' roles, and carried in the document's
`constructs` table. The readers check members, references and rules from the
declaration; the backends dispatch on shape and identity and render the kind's
name from `kind.name`. No source outside fixtures, goldens and tests names a
domain construct kind.

## Rationale

**The module already owns the object type.** Its fields, roles, allowed links
and extraction live in the manifest. The construct is one more property of the
same object type, versioned with it and digested with it.

**The vocabulary is what the contract can check.** A reader can verify that a
member is present, forbidden or optional, that a reference names a type carrying
an admitted role, and that a selected rule holds, without knowing what the kind
means. What the kind means is its `meaning` id, which QSpec owns and the IR
carries opaquely.

**A new domain costs no contract release.** A port in the systems module is an
`interface`-shaped construct carrying `owner`, `direction`, `interfaceType` and
`multiplicity`; a connection is a `record`-shaped construct carrying
`flowDirection` and its two ends, `sourceEnd` and `targetEnd`, each end naming a
type and an optional `multiplicity`. Both are declared in the systems manifest
and read, checked and generated by the code that reads business constructs
(FR-142-AC-10).

**The document is self-describing.** Each `constructs` entry carries
`moduleVersion` and `manifestDigest`, so a reader checks a document without
loading the module, and a consumer can tell which module release a construct was
declared under.

**Refusal names the author.** A declaration the frontend cannot read yields one
blocking diagnostic naming the module and the object type (FR-143-AC-8), so a
manifest defect is reported against the manifest that holds it.

## Consequences

- The IR contract is `2.0.0`. A type's `kind` is a core kind or `{module, name}`,
  and a document using a module kind carries exactly one `constructs` entry for
  it. A kind with no entry, an entry no type uses and a duplicate entry are each
  refused.
- `schema/semantic/v1/construct-vocabulary.json` is the one source of the core
  vocabulary, its member defaults, reference items, rule requirements and the
  optional flags a declaration carries (`immutable`, default `false`); the Rust,
  TypeScript and Python readings agree with it (FR-142-AC-11).
- `crates/semantic-ir` is the one authority for the construct rules. The Node
  compiler and the Python backend read the same vocabulary file and check the
  schema layer only — the closed terms, member presence and a list member a
  `nonEmpty` rule requires — so a rule is implemented once
  (FR-142-AC-11, FR-142-AC-14).
- The frontend reads a declaration through one seam,
  `CompiledArchetype::construct()`
  ([agent-ix/quire-rs#445](https://github.com/agent-ix/quire-rs/issues/445)).
- A domain module gains a construct by editing its manifest. A construct needing
  a member, shape or rule the vocabulary lacks is a contract change, filed
  against this repository.
- The business module's `meaning` ids for `domain`, `repository`,
  `state_machine` and `process` are placeholders until QSpec allocates them.
  The IR carries them opaquely, so allocating them changes the module and no
  contract.

## Status

**Accepted.** Normative for the semantic IR under FR-142 and the extraction
frontend under FR-143, ruled under
[agent-ix/filament-core-data#172](https://github.com/agent-ix/filament-core-data/issues/172),
and gated by TC-1786..TC-1794.
