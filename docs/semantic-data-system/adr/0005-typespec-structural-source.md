# ADR-0005: Use TypeSpec as the structural schema source

## Context

[ADR-0004](0004-conditional-typespec-source.md) made TypeSpec conditional on a
feasibility gate resolved by
[filament-core-data#4](https://github.com/agent-ix/filament-core-data/issues/4).
The spike under `spikes/typespec-feasibility/` compiled a three-package modular
TypeSpec source, ran the official JSON Schema and Protobuf emitters, emitted a
deterministic source-located semantic IR through a custom `$onEmit` emitter, and
generated Rust/Serde, TypeScript, and Python/Pydantic consumers that all pass the
same golden fixture. Twelve of fifteen recorded capabilities pass.

The spike report nevertheless recommended a hold, because it applied a pass rule
that was not in ADR-0004: a capability needing custom code counted as partial
unless a production owner, budget, and upgrade SLA had already been accepted. Two
capability rows encoding that rule were added during the spike. The owner
rejected that rule on 2026-09-03 and recorded the decision on issue #4.

## Decision

TypeSpec is the structural schema source for semantic packages.

- Package definitions, types, constraints, versioning and deprecation markers are
  authored in TypeSpec, organised as modular packages that import a small
  semantic core.
- JSON Schema 2020-12 and Protobuf are generated by the official TypeSpec
  emitters. They are projections, never authoring sources.
- The semantic IR emitter, the Rust/Serde and TypeScript backends, and the
  `datamodel-code-generator` Python integration are Agent IX-owned code in this
  repository, per [ADR-0002](0002-generated-package-ownership.md). The issue #4
  prototypes are the seed for that code.
- The owner of the compiler, the IR, and every backend is the repository owner.
  Ownership is not a gate that later tickets re-litigate.
- The official JSON Schema emitter's relative `$id` for the shared
  `Record<string>` helper is a tracked defect
  ([filament-core-data#31](https://github.com/agent-ix/filament-core-data/issues/31))
  with a pinned validation-alias workaround until fixed.

## Consequences

- Downstream contracts may require TypeSpec inputs. The semantic IR/package
  specification ([issue #9](https://github.com/agent-ix/filament-core-data/issues/9))
  specifies the TypeSpec frontend, not a source-neutral one.
- The compiler frontend ticket promotes the spike emitter rather than writing a
  JSON Schema reader.
- Protobuf field numbers, Markdown mappings, SQL mappings, and analytical
  profiles remain explicit package/mapping metadata beside the TypeSpec source.
- A TypeSpec compiler upgrade is qualified against the retained golden fixtures
  before it is pinned.

## Alternatives considered

- **Modular JSON Schema 2020-12 as the authoring source:** rejected. It was
  recorded as a fallback in ADR-0004 without an owner request, and the issue #4
  evidence shows TypeSpec works end to end. JSON Schema stays a generated
  projection.
- **Adopt Avro as the universal source:** rejected, unchanged from ADR-0004.
- **Python decorators as the source:** rejected, unchanged from ADR-0004.

## Compatibility

The current Avro contract, generated bindings, and consumers are unchanged until
the compatibility, migration-readiness, and cutover gates pass.

## Supersession

Supersedes [ADR-0004](0004-conditional-typespec-source.md), which is retained as
historical. The spike evidence under `spikes/typespec-feasibility/` is frozen as
the record of what was measured on 2026-08-30; its report text predates this
decision.
