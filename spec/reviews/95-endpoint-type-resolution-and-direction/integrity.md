# SR-215: integrity review of the endpoint type-resolution and direction batch

## Summary

The batch holds the refusal-over-default line in its vocabulary work — the four
directions and the six type kinds are closed, named, and refused rather than
defaulted — but its central no-inference claim is unbacked: nothing establishes
that an authored export `kind` is the kind the native artifact declared, and the
one requirement that would ground it (FR-129) states a digest-recomputation
refusal without ever saying where the native bytes enter admission. Fourteen
findings follow, four of them high.

## Findings

| ID | Severity | Summary | Refs | Escape Cause |
|----|----------|---------|------|--------------|
| FND-901 | high | The producer authors the export mapping's `kind` member itself (FR-116 puts export mappings in the producer's own bundle document), so FR-127's "SHALL NOT select, default, or narrow the native export kind … which the native artifact alone declares" is a provenance claim with no check behind it: a mapping declaring `object` for a native `scalar` export is admitted by every criterion FR-127 states. FR-127-AC-4 ("each admitted, with the producer selecting none of the six") asserts the unobservable — no test can distinguish "the producer selected `object`" from "the native artifact declared `object`" against an authored member. Kind substitution therefore passes unnoticed, which is exactly the defect the requirement exists to close. | FR-127 Description, Behavior ("SHALL NOT select, default, or narrow"), FR-127-CON-5, FR-127-AC-4; crates/baseline-producer/src/export.rs `ExportRecord.kind`, `DeclaredExports::validate_kind` (kind checked only for membership in `TYPE_KINDS`) | missing-requirement |
| FND-902 | high | `RelationshipEndpoint` carries its own `typeIdentity` (FR-115), and nothing in FR-115, FR-127 or FR-129 requires it to equal the `typeIdentity` of the `EndpointDeclaration` it joins through `endpointIdentity`. FR-127 declares only endpoint-declaration type identities into the resolution vocabulary, so a relationship end may name a type identity that is in no vocabulary, owes no export mapping, and refuses nothing. FR-129-AC-4's "resolves its `source` and its `target` to two distinct native type exports" is satisfiable by two relationship-side spellings that resolve nothing at all. This is an identity substitution admitted silently at the exact seam the batch claims to close. | FR-115 Behavior (`typeIdentity` on each endpoint record), FR-127 Behavior (vocabulary built from endpoint declarations only), FR-129-CON-6, FR-129-AC-4; crates/baseline-producer/src/export.rs `DeclaredExports::new`, relationship.rs `RelationshipEndpoint::validate` | missing-requirement |
| FND-903 | high | FR-129 states a refusal ("If a fixture's declared native raw-byte digest does not equal the recomputed SHA-256 of the bytes it names, then the producer SHALL refuse the fixture") whose input the batch never admits anywhere. FR-117 closes the static bundle over nine content member classes, none of which is native artifact bytes; FR-129-CON-7 forbids environment, working-directory and network input; FR-129-CON-8 and US-018's rejected options forbid vendoring a copy. Every route to holding the bytes is closed, so the refusal is unimplementable as stated and the fixture's admission remains exactly the shape-only check US-018 exists to replace. | FR-129 Behavior, FR-129-CON-1/CON-7/CON-8, FR-129-AC-1/AC-5/AC-8, US-018 "Options (Exploratory)"; FR-117 nine content classes; crates/baseline-producer/src/static_bundle.rs `StaticProducerBundle` | missing-requirement |
| FND-904 | high | An identity that is both a declared record and an endpoint's named model type has no admissible bundle, and FR-127 does not say so. The Description requires refusing a bundle "in which a named model type … resolves through an export mapping whose kind names something other than a type", while the Behavior bullet and FR-127-AC-6 require that identity to retain the record's exact-kind admission (`component`/`endpoint`/`relationship`) and to refuse a mapping carrying a type kind. Both a record-kind mapping and a type-kind mapping are therefore refused, and no mapping at all refuses under `ENDPOINT_TYPE_EXPORT_ABSENT`. A state the requirement explicitly contemplates is unreachable rather than refused with a reason. | FR-127 Description, Behavior ("SHALL keep a declared model type and a declared record distinct vocabulary members"), FR-127-AC-6; crates/baseline-producer/src/export.rs `Admits`, `DeclaredExports::new` (`or_insert` keeps the record admission) | wrong-requirement |
| FND-905 | high | "The producer SHALL NOT carry a native raw-byte digest composed of repeated placeholder fill in any fixture offered as evidence of type resolution" is a prohibition decided by guessing. "Repeated placeholder fill" is undefined, no refusal or code is named for it, and a producer can only classify a digest as placeholder by inspecting its text — inference of precisely the kind the batch bans elsewhere. The checkable property (the digest equals the SHA-256 of bytes the producer holds) is FND-903's, which is unimplementable; this bullet is the unimplementable rule's unfalsifiable substitute. | FR-129 Behavior (placeholder-fill bullet), FR-129 Description; fixtures/baseline-1-2/static-bundle-a.json (`sha256:5555…`, `sha256:8888…`) | wrong-requirement |
| FND-906 | medium | FR-128 makes an out-of-vocabulary direction unrepresentable and then delegates the wire case to "the wire-shape refusal FR-117 owns" (FR-128-AC-3). That refusal is the generic unreadable-document refusal: it names neither the offending relationship nor the offered direction value, so an unknown direction is indistinguishable from any other malformed document. Every other member of a relationship record whose absence or foreignness refuses names its subject; direction becomes the single exception, and the batch states no obligation to name it. | FR-128 Outputs, Behavior ("refuse it at the admission seam"), FR-128-AC-3; crates/baseline-producer/src/refusal.rs `INVALID_PRODUCER_DOCUMENT`; contrast FR-117-AC-2 and FR-127-AC-2/AC-3 | missing-requirement |
| FND-907 | medium | FR-128 states "The producer SHALL NOT default an absent direction to any of the four" but never says what an absent direction does instead. A required closed member makes absence a parse failure carrying no relationship identity, so the one prohibition the requirement states about absence has no stated positive outcome — the pattern FR-117 sets (an absent member refuses naming that member) is not followed, and the absent case appears in no acceptance criterion. | FR-128 Behavior, FR-128-CON-3, FR-128-AC-5 (covers defaulting between the two, not absence); FR-117-AC-2 | missing-requirement |
| FND-908 | medium | FR-127 requires each model type to resolve through "exactly one export mapping" and names refusals for zero mappings and for a wrong kind, but states no outcome for two mappings resolving one model type within a single correspondence record. The cross-bound prohibition FR-127 cites covers mappings owned by *different* producer objects; a duplicate under one producer object is prohibited by "exactly one" without any stated refusal. The spike reaches for `EXPORT_CROSS_BOUND` with a different message under the same code, which is a decision the spec left to the implementation. | FR-127 Description, Behavior ("SHALL owe exactly one export mapping"), FR-127-AC-7; crates/baseline-producer/src/correspondence.rs `validate_correspondence_set` (duplicate under one owner also raises `EXPORT_CROSS_BOUND`) | missing-requirement |
| FND-909 | medium | `undirected` is specified only negatively — "admit neither traversal as oriented", "SHALL NOT supply an orientation" — so nothing distinguishes an undirected relationship from one that admits no traversal whatsoever, and a consumer must decide whether the relationship holds symmetrically or not at all. The batch insists `undirected` and `bidirectional` are distinct authored states without stating what the distinct state *admits*; the spike's reading (both traversal predicates false) is a choice the spec does not make and arguably inverts the ordinary meaning of an undirected edge. | FR-128 Behavior (`undirected` bullet), FR-128-AC-5; crates/baseline-producer/src/relationship.rs `RelationshipDirection::admits_source_to_target` / `admits_target_to_source` / `is_oriented` | missing-requirement |
| FND-910 | medium | FR-127-CON-3 removes `population` from the export vocabulary entirely ("unrepresentable rather than refused"), but FR-120 requires the producer to *admit* a `population`-kind correspondence export on an assessment document and to name that export kind in its refusals. Making the kind unrepresentable in the one export vocabulary makes FR-120-AC-7 and FR-120-AC-10 unimplementable, and FR-127 cites neither FR-120 nor FR-117 in its dependencies. The batch moves a value from representable-and-refused to unrepresentable without checking who still needs to represent it. | FR-127 Description, Behavior, FR-127-CON-3, FR-127-AC-8; FR-120 Behavior (admits `population` on an assessment document), FR-120-AC-7, FR-120-AC-10, FR-120-CON-4; crates/baseline-producer/src/export.rs `ExportKind` | wrong-requirement |
| FND-911 | medium | FR-129 requires every native export whose kind the static vocabulary cannot spell to be omitted from the fixture, and that omission to be "recorded as a stated partition of the assessment half rather than as an unexplained absence" — but names no member, document, or artifact that carries the record. An unlocated statement verified by Inspection is indistinguishable from the unexplained absence the bullet forbids, and US-018-EX-3 rests entirely on it. | FR-129 Behavior (omission and recording bullets), FR-129-AC-6, US-018-EX-3 | missing-requirement |
| FND-912 | low | FR-127 obliges the producer to "retain the exact ordered export path … in the order the native artifact declared it" but names no refusal for a reordered, truncated, or re-segmented path, and FR-127-AC-1 asserts only that the path is readable as a separate member. A silently reordered path is therefore admitted, while the neighbouring no-inference rule about path segments is refused-and-named. Ordering is asserted as a property nothing observes. | FR-127 Behavior (ordered-path bullet), FR-127-AC-1; crates/baseline-producer/src/export.rs `ExportRecord::validate` (checks non-empty segments only) | correct-requirement-no-evidence |
| FND-913 | medium | FR-129 now contradicts itself about regeneration. A Behavior bullet obliges the producer to "pin the named artifact's identity and revision … so a regenerated artifact carrying a changed export table refuses rather than resolving against a table the fixture never selected", while the pinned-contract entry in the same requirement's Dependencies states that "a change on the consumer side, including a regenerated package with a changed export table, is not detected by this requirement". Both cannot hold. Pinning identity and revision detects nothing in any case: this repository's own ruling records the native revision as an editable authority label rather than a formal revision, so a regenerated artifact keeps its pin and only the byte digest of FND-903 would move. US-018 raised this as an open question introducing no requirement; the requirement now answers it in two opposite directions. | FR-129 Behavior (pin bullet), FR-129 Dependencies (pinned consumer contract entry), US-018 "Notes (Informative)"; spec/log.md 2026-09-11 item (a) on `NativeSource.revision` | wrong-requirement |
| FND-914 | low | FR-129's constraint table skips `FR-129-CON-4` entirely — it runs CON-1, CON-2, CON-3, CON-5, CON-6, CON-7, CON-8 — so any matrix or traceability pass over this requirement will carry a hole whose cause is invisible, and a later author may reuse the free id for an unrelated constraint. | FR-129 Constraints table | missing-requirement |
