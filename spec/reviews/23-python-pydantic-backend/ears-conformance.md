# EARS conformance review

## Summary

The 141 SHALL-bearing statements of issue #23 (FR-072 through FR-080, NFR-026
and NFR-027; US-013 read for context only — it carries no SHALL) were read one
by one for pattern fit. Quire 0.31.0 (engine 0.46.0) reports
`156/157 docs grammar-clean (99%); 1 grammar finding(s): ears:non-singular=1`
over the whole corpus, and that single finding is on
`FR-031-define-the-semantic-core-declaration-grammar.md` line 56 — `The package
SHALL be publishable to the internal registry … and SHALL NOT be marked
private, because …` — which is outside this review's scope. **Zero `[ears:*]`
and zero `[quality:*]` findings fall on any file in scope**, independently
confirmed here.

Every finding below therefore comes from reading. The engine is clean because
its grammar pass reads bulleted Behavior statements and Constraints rows, and
no bullet or row in this bundle carries two `SHALL` (verified: zero matches for
a bullet or table row containing `SHALL … SHALL`). The compound obligations
have all migrated into the Description and Statement **paragraphs**, which the
pass does not scan — seven of the eleven documents carry a Description or
Statement with two to five `SHALL` in one sentence. Beneath that, three
structural defects dominate: an obligation cycle between a profile's digest and
the verdict recorded in it; a fail-on-degradation rule that cannot coexist with
the requirement to measure and emit the families that degrade; and a bundle
that has almost abandoned the `If … then …` form — 3 canonical unwanted-behaviour
statements against roughly 25 unwanted cases, where the issue #19 bundle
reviewed by SR-067 carried 40.

| FND-1177 | high | FR-073 makes a profile's digest and its verdict mutually invalidating. `Each profile SHALL carry … the verdict reference into FR-077`, `profileDigest SHALL return the SHA-256 over the profile's canonical JSON`, and `The qualification report SHALL cite the profile digest beside each verdict, so that editing a profile changes its digest and invalidates the verdict that cites it` form a cycle: recording a verdict edits the profile, which changes the digest, which invalidates the verdict just recorded. FR-073-CON-3 (`Adding a profile SHALL add a qualification verdict in the same change`) closes the loop and makes the first qualification of any new profile unsatisfiable. FR-073-AC-7 only exercises option changes and so never detects it. Either exclude `verdict` from the digest input and say so in the digest statement (`profileDigest SHALL return the SHA-256 over the profile's canonical JSON excluding the verdict reference`), or move the verdict reference out of the profile into `report.json`, which already carries the profile id. | FR-073, FR-077 |
| FND-1178 | high | FR-078 and FR-077 cannot both be satisfied for a lossy family, and nothing states which yields. | FND-1182 | medium | NFR-027's Statement hangs four unrelated obligations off a determinism subject by participial clause: `Two clean generations from the same input, profile, and recorded toolchain SHALL produce byte-identical artefacts and an identical fingerprint, with a regenerable and --check-verified qualification report, publishing nothing, migrating no consumer, and leaving every artefact outside the permitted paths byte-identical to origin/main`. | FND-1187 | low | Pattern-keyword misuse and acceptance criteria written as observations. **`Where` is used for runtime conditions rather than for optional features** in all four of its occurrences — FR-074 `Where the pass cannot close a measured gap`, FR-077 `Where the owned adapter … closes a gap` and `Where a schema rewrite cannot close a gap`, FR-079 `Where a family's verdict is not-qualified` — each is a data-dependent condition evaluated per run, so the form is `If … then …`; SR-067 recorded issue #19 reserving `Where` for genuine optional-feature cases. **Six acceptance criteria state an observation rather than a decidable pass/fail:** NFR-027-AC-8 `Reverting this change restores the tree to its pre-change state exactly` is true of every revert and tests nothing this change controls; NFR-027-AC-10 `Nothing was published: no PyPI upload …` names an event outside the repository that no in-repo check can observe (the other two clauses can be, and already are, by NFR-027-AC-5); FR-078-AC-3 requires `the sanctioned census equals the number of genuinely unconstrained schema nodes` with no statement defining who counts that number independently of the inspection under test; FR-077-AC-9 requires `the unmet count matches the number of rows the blocking dependency prevents` with the same missing independent count; FR-079-AC-2 turns on `imports cleanly`, which is undefined (the Behavior bullet is precise — no `PydanticUndefinedAnnotation`, no unresolved `ForwardRef` — so state that); FR-074-AC-3's second half, `where generating from the unprepared document yields extra='allow'`, asserts a property of the upstream generator rather than of this system, and goes red on an upstream default change that is not a defect here.
