# Failure-domain review

## Summary

The #87 change states one identity-minting function in `contracts-v1.md`
§Identity minting and names three implementations of it. Reading the stated
function against the grammar it consumes (`Identifier` is
`^[A-Za-z_][A-Za-z0-9_]*$`, FR-031) and against the two minters it names
(`src/compiler/frontend/typespec/identity.mjs`, `lower.mjs`;
`crates/extraction-frontend/src/identity.rs`) finds that the function is not
yet one function at its edges. Two highs: the contract's sentence "for a name
that is already an `Identifier`, the slug is the name verbatim" is false for
any name carrying `_`, and FR-095 builds its `type/` rule on it, so the two
frontends mint `type/Config_Version` and `type/Config-Version` for one record;
and the contract's closing rule (`DUPLICATE_IDENTITY` at the later declaration
with the earlier locus in `related`, `UNSLUGGABLE_NAME` only for an empty slug)
is stated as shared but is FR-095's alone — FR-053 raises `UNSLUGGABLE_NAME`
for a slug fold and leaves every other collision to the reader, and
FR-095-CON-4 freezes that. The mediums are the alias `displayName` the
contract does not define and FR-093 and `lower.mjs` derive differently (which
breaks the parity FR-098 now calls unconditional), the case-folding
`diagnosticCode` that gives the contract's explicitly distinct `Status` and
`status` one code with no owner checking it, the carve-outs from the closing
rule that FR-093 keeps under `DUPLICATE_TYPE_NAME` while the contract admits
none and orders collisions by a locus a kernel definition does not have, and
FR-034 named as an implementation of a rule whose root and closing rules it
does not state. No trust-boundary or topological hazard exists in this change;
identity is a pure function of declaration and package on both sides, with one
order-dependence at the kernel slot noted under FND-1524.

## Findings

| ID | Severity | Summary | Refs | Escape Cause |
|---|---|---|---|---|
| FND-1520 | high | `contracts-v1.md` §Identity minting: "For a name that is already an `Identifier`, the slug is the name verbatim" is false. FR-031 gives `Identifier` the pattern `^[A-Za-z_][A-Za-z0-9_]*$`, so `Config_Version`, `created_at`, and `_draft` are `Identifier`s whose slugs are `Config-Version`, `created-at`, and `draft`. FR-095 "Node identities" builds its `type/` rule on the false sentence — "`<Name>` is the record's `displayName` verbatim … verbatim and slugged are the same string, because a `displayName` is an `Identifier` and `slug` maps an `Identifier` to itself" — and `identity.rs::type_identity` passes the name through unslugged, while `identity.mjs::mintIdentity` slugs every part. A spec-bundle record whose frontmatter `name` is `Config_Version` therefore mints `type/Config_Version` and the TypeSpec model `Config_Version` mints `type/Config-Version`: the one declaration the rule exists to unify gets two identities, and the `field/`, `constraint/`, `relationship/`, `operation/`, and `clause/` tails of that record diverge with it (`field/Config_Version-id` against `field/Config-Version-id`). `type/<Name>` must be `type/slug(Name)` on both sides, the contract sentence must say the slug is verbatim only for `[A-Za-z0-9]+` names, and FR-095's "verbatim" clause and its justification must go; the AC-16 table needs a row with an underscore in the owner name so the divergence cannot return. | contracts-v1.md §Identity minting, FR-095, FR-095-AC-6, FR-095-AC-16, FR-053, FR-031 | wrong-requirement |
| FND-1521 | high | The contract's two closing rules are stated as part of the rule "implemented unchanged by every frontend", but only FR-095 implements them. The contract says a collision raises `DUPLICATE_IDENTITY` at the later declaration by path, line, column, with the earlier locus in `related`, and `UNSLUGGABLE_NAME` fires only for an empty slug. FR-053 line 65 and FR-053-AC-10 say two names slugging to one identity raise `agent-ix.compiler.UNSLUGGABLE_NAME` (so `created_at` beside `created-at` is `UNSLUGGABLE_NAME` in one frontend and `DUPLICATE_IDENTITY` in the other, and the code has two meanings), and `lower.mjs` lines 331–339 check slug collisions over declaration names only: an artifact `NoteRevision` beside `Note { @minValue(1) revision }` — the contract's own example — mints two `type/NoteRevision` in the TypeSpec frontend with no frontend diagnostic and is refused by the FR-050 reader (`reader.mjs` 460–466) as `agent-ix.semantic-ir.DUPLICATE_IDENTITY` "at the second declaration in document order", with no `related` locus. FR-095-CON-4 then forbids changing any byte of `src/compiler/**`, so the contract's closing rule cannot become shared under this change. State the closing rules as FR-095's (and say which code, owner, and locus rule the TypeSpec frontend applies to the same failure), or drop CON-4's `src/compiler` freeze for the two collision paths and add the cases to the AC-16 table; either way the contract must stop claiming a disposition FR-053 does not have. | contracts-v1.md §Identity minting, FR-053 (line 65), FR-053-AC-10, FR-095, FR-095-CON-4, FR-095-AC-14, FR-096 | wrong-requirement |
| FND-1522 | medium | The contract defines the alias identity `type/<Name><Field>` and nothing about the alias `displayName`, yet the parity projection of FR-098 keeps `displayName` and FR-098-AC-7 now asserts byte equality "unconditionally". FR-093 sets the alias `displayName` to `<DisplayName><Field>` with `<Field>` the capitalised slug (`created_at` → `NoteCreated-at`); `lower.mjs` line 806 sets `aliasName` to `ownerParts[0] + capitalize(property.name)` over the raw property name (`NoteCreated_at`), while its identity is `type/NoteCreated-at`. Any shared case with a constrained snake_case field therefore fails parity on `displayName` while agreeing on identity, and `records-and-scalars` passes only because `revision` has no separator. `semantic-ir.schema.json` gives `displayName` only `minLength: 1`, so neither reader catches a `displayName` that is not an `Identifier`. Define the alias `displayName` in the contract (recommend: equal to the identity tail, `<Name><Field>` over the slug) and add an AC-16 row for a constrained `created_at`. | contracts-v1.md §Identity minting, FR-093 ("The fields"), FR-098-AC-7, FR-095-AC-16, FR-053 | missing-requirement |
| FND-1523 | medium | `UPPER_SNAKE` upper-cases, so the `diagnosticCode` folds the case the identity preserves. The contract rules that `Status` and `status` "are distinct identities, not a collision", and both records with a field `id` carrying `min` then emit one `agent-ix.<pkg>.STATUS_ID_MIN`; `Note`/`note`, `createdAt`/`createdat`, and `NoteRevision` (an author type constrained on `x`) beside `Note.revision` … `x` likewise. FR-093 raises `DUPLICATE_CONSTRAINT` only when "two constraints of one record yield the same `diagnosticCode`"; FR-053 has no code-collision rule; `crates/semantic-ir/RULES.md` and `common.schema.json` state no uniqueness over `diagnosticCode`. State the code's uniqueness scope (per document, recommended) and the code that refuses a cross-record collision, in the contract, so both frontends own it; FR-095-AC-14's `Status`/`status` positive case then needs a constrained field on each to prove the disposition. | contracts-v1.md §Identity minting, FR-093, FR-093-AC-13, FR-095-AC-14, FR-053 | missing-requirement |
| FND-1524 | medium | The closing rule admits no carve-outs, but FR-093 keeps three, and the rule's ordering has no answer for a locus-less party. (a) FR-093 "The enumerations": two rows slugging alike raise `DUPLICATE_TYPE_NAME` at the second row — the contract says two declarations minting one `variant/` identity are `DUPLICATE_IDENTITY`; one failure, two codes, and `negatives/DUPLICATE_TYPE_NAME` and `negatives/DUPLICATE_IDENTITY` both plausibly claim it. (b) A `displayName` equal to a kernel scalar name is `DUPLICATE_TYPE_NAME` in FR-093 and FR-095-AC-14, while the contract lists `type/<KernelScalar>` as a slot the rule mints and says a collision is `DUPLICATE_IDENTITY`; FR-053 states nothing for `model String`, and `lower.mjs::useKernel` skips minting when `definitions` already holds `type/String`, so which node owns the identity — and what every `string`-typed field's `typeRef` resolves to — depends on whether the author's model was lowered before the first kernel use. (c) The order "package-root-relative source path, then start line, then start column" is undefined when one party is a kernel definition (no declaration) or an FR-034 node with a generated origin; FR-095 says "bundle-root-relative", the contract "package-root-relative". State in the contract that equal-name refusals (`DUPLICATE_TYPE_NAME`, the engine's `DUPLICATE_FIELD`) run first and `DUPLICATE_IDENTITY` is the residual over distinct names, that a kernel definition is the earlier party always, and one root for the path order. | contracts-v1.md §Identity minting, FR-093 ("The enumerations", "The record"), FR-095, FR-095-AC-14, FR-053, FR-098 (negatives inventory) | missing-requirement |
| FND-1525 | medium | The contract names the semantic-core lowering (FR-034) as the first of three implementations of the whole rule, "unchanged". FR-034 roots every identity at `ix://<org>/<repo>/` (lines 31, 54) where the contract roots at the package identity — FR-053 itself records the difference ("rooted at the package identity rather than at `<org>/<repo>`") — and FR-034 states no `variant` slot (FR-053 calls it "this requirement's addition"), no `slug`, no `DUPLICATE_IDENTITY`, and no `UNSLUGGABLE_NAME`; its one added sentence claims only "the identity, alias, and `diagnosticCode` rules above". Whoever runs FR-034's lowering on a colliding or unsluggable declaration has no stated disposition, and FR-053-CON-1's differential test cannot compare a closing rule one side lacks. Either narrow the contract's claim to what FR-034 states (the shapes and the `diagnosticCode`, under its own root), or add the slug, the `variant` slot, and the two closing rules to FR-034 with the package-identity root. | contracts-v1.md §Identity minting, FR-034, FR-053, FR-053-CON-1 | wrong-requirement |
| FND-1526 | low | Parts are slugged, may contain `-`, and are joined by `-`, so the join is not injective and the contract's "occupies exactly one of these slots" hides that the `field` slot hosts two shapes: a field `create_at` and an operation `create` with a parameter `at` on one record both mint `field/Note-create-at`; a clause `a-b` and a clause `a_b` mint one `clause/`. FR-095's collision check "over every minted identity of one lift" catches these on the spec-bundle side; on the TypeSpec side `lower.mjs` checks declaration names only, and the compiler reader's per-definition loop (`reader.mjs` 436–448) walks `fields`, `variants`, `constraints`, `relationships`, `operations`, `clauses` and not `operations[].params`, so a field–parameter collision reaches the emitted document. ## Failure Dispositions

| Failure | Required disposition |
|---|---|
| A record or field name that is an `Identifier` carrying `_` | Slugged on both sides; `type/Config-Version`, `field/Config-Version-created-at`; one AC-16 row proves it |
| Two declarations minting one identity in the TypeSpec frontend | One code, one locus rule, one `related` shape, stated for FR-053 in the contract or the closing rule declared FR-095-only |
| A constrained snake_case field | Alias `displayName` defined by the contract and equal on both sides |
| Two constraints in one document with one `diagnosticCode` | Refused by the producer at the later constraint, on both sides, with a code the contract names |
| Two enumeration rows slugging alike | One code (`DUPLICATE_IDENTITY` under the contract) or a stated carve-out |
| An author type named as a kernel scalar | Refused before any kernel use, in both frontends, never captured by declaration order |
| A collision whose earlier party has no locus | Kernel definition is the earlier party; FR-034 generated-origin nodes ordered by their owner's locus |
| A field and a parameter of one owner minting one `field/` identity | `DUPLICATE_IDENTITY` at the later declaration; checked across slots, not per list |
