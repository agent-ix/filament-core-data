# Evidence-method review

## Summary

The issue #22 slice carries **216** obligations — 165 acceptance criteria and 51
named constraints across FR-063..FR-071, NFR-024 and NFR-025 — plus 12 NFR-024
metric rows, 14 NFR-025 metric rows, and 100 matrix rows (TC-745..844). The
`Verification` column distributes as Unit 43, Test 28, Integration 21, Static 19,
Analysis 15, Property 12, Compile 12, Snapshot 10, Fuzz 4, Manual 1; the matrix
`Type` column as Unit 36, Integration 21, Property 9, Analysis 8, Compile 8,
Static 8, Snapshot 7, Fuzz 3. `Test` in a `Verification` cell is the repository's
method-class convention (FR-042, FR-052) and is correct; SR-052 FND-794 settled
that the defect is an *evidence kind* in that cell, not `Test`. Thirty-five
obligations authored `Test` are discharged by rows of some other type, which is
expected. What is not expected, and is the recurring finding, is that **thirty
obligations name a value that is itself in the matrix vocabulary and still
disagree with the row's Type** (FND-1033).

Three structural gaps dominate, and all three sit under the ticket's own headline
acceptance criteria.

First, **there is no payload corpus**. The issue's criterion "Runtime validators
reject every negative fixture without unsafe casts" has no negative fixture to
run against. `conformance/schema/input-bundle.schema.json` admits exactly
`{ir, manifest, manifestDigest, lock, profile, mappings, consumerPolicy}` — no
instance data — and `fixtures/semantic/v1/negative/cases.json` entries are
`{id, schema, base, set{path,value}, code}` mutations of *contract documents*,
not instances of a generated domain type. FR-070-AC-11 names "every positive
payload a case supplies"; no case supplies one. FR-066-AC-1 and FR-066-AC-2
depend on an unspecified projection from a contract document to an instance
(FND-1030).

Second, **the discriminator against tuning is absent**. `conformance/thresholds.json`
proposes `mutationDetectionScore: 1.0` and `constructRegisterCoverage: 1.0` for
the `typescript-backend` slot. FR-070 mentions neither, and
`conformance/runner/differential.mjs`'s `mutationScore()` computes detection from
`oracleVerdict(cases[mutation.detectedBy])` — it measures the *oracle*, not an
adapter — so the proposed threshold is not measurable by the machinery that
exists (FND-1031). This matters because agreement on 111 committed cases is
reachable by fitting: FR-068-CON-1, FR-069-CON-1 and FR-070-AC-5 ban *imports* of
the oracle and the compiler's reader, which a static scan can decide, but no
method in the bundle distinguishes an independently derived implementation from a
transcription of `conformance/oracle/oracle.mjs`, and FR-070-AC-6 does not close
it either. AC-6 proves the comparison is load-bearing — that answering with the
oracle's verdict would hide a seeded defect — which is a genuinely good and
unusual criterion. It says nothing about an implementation that never calls the
oracle and simply agrees with it on exactly the 111 inputs it was written
against. Answering the parent's question plainly: **no, nothing in this bundle
would detect transcription.** The two methods that would are a per-adapter
mutation score and a hold-out — documents the corpus does not contain, decided
against a rule quoted from `contracts-v1.md`. The corpus's own `derivedFrom`
pattern is the model: FR-068 already carries a rule/code table, and a citation
column on it would make each rule's provenance checkable the way each case's
expectation already is.

Third, **the generated TypeScript has no independent oracle at all**. The corpus
judges the IR-reading half — `resultState`, `diagnostics`, `normalized`,
`classification` — and cannot judge emitted source. Every `Snapshot` baseline in
FR-064 and FR-071 is minted by the backend and then used as its own oracle, which
is `provenance.blessedFromRun` one layer down, the defect the corpus was built to
prevent (FND-1032). `tsc` passing is necessary and not sufficient: a package of
`any` typechecks too, so the discriminating evidence is the *negative* compile
fixtures (FR-064-AC-5, FR-064-AC-6, FR-065-AC-9, FR-066-AC-17, FR-067-AC-4,
FR-071-AC-9, FR-071-AC-10) and the no-`any` scans, and neither FR-065-AC-8 nor
FR-070-AC-10 nor NFR-024-AC-11 says so.

Three narrower method errors follow. Eleven obligations are authored `Static`
whose subject is *generated output* rather than committed source, which cannot be
decided without first running the backend (FND-1035). Twelve `Property`
obligations and nine `Property` rows have no generator: `fast-check` is absent
from `pnpm-lock.yaml`, `hypothesis` appears in `poetry.lock` only inside a
`pytest` extra, and NFR-025-AC-4, FR-069-AC-15 and FR-065-CON-4 forbid adding one
— FR-069-AC-3 asks for idempotence "for generated documents" outright (FND-1034).
And run-A-versus-run-B determinism is typed `Snapshot` again at NFR-024-AC-1..3
and FR-067-AC-8, the exact shape SR-052 FND-792 recorded for issue #20 and asked
to be retyped; inside this one bundle the same shape is `Snapshot`, `Integration`
(FR-071-AC-2, FR-071-AC-3) and `Property` (FR-066-AC-16) (FND-1036).

Nothing here matched `fault-detection-unmeasured` by escalation, because no
obligation is bound to a run yet — all 100 rows are `🚧`. The mutation measure of
FND-1031 is the catalog's `mutation-testing` arriving by design, as it did for
issue #20 at SR-052 FND-805; the difference is that issue #20 built it and this
ticket does not use it.

Acted on in the review pass: the two findings that left a headline criterion
with no oracle were closed — FND-1030's absent payload corpus became an authored
instance corpus checked against a second, independently written decider, and
FND-1031's unmeasurable anti-tuning gate became a committed first-run divergence
count and an explicit statement that `mutationDetectionScore` scores the oracle
rather than an adapter. The evidence-vocabulary findings are recorded against
this ticket's own matrix reconciliation, which had not run when this review was
written. The per-finding record is the disposition table at the end of this
document.
