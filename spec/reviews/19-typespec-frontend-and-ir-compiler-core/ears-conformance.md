# EARS conformance review

## Summary

The 173 SHALL/MAY-bearing statements of issue #19 (FR-045 through FR-052 and
NFR-019 through NFR-021; US-010 read for context only) were read one by one for
pattern fit. Every statement carries an explicit subject, no statement uses a
vague response verb from the `support`/`handle`/`manage`/`process`/`provide`/
`enable` lexicon, no statement uses a non-canonical `On`/`Upon`/`After`/`During`
trigger, and the unwanted-behaviour obligations consistently use the
`If … then <actor> SHALL raise <code> at <locus>` form — 40 of them name both a
closed diagnostic code and the position that declared the defect. The scope
contains no `MAY` statement at all; the only permissive `may` is quoted policy
prose inside FR-051's documentation obligation.

Quire 0.31.0 (engine 0.46.0) reports **1 grammar finding** over the corpus —
`119/120 docs grammar-clean (99%); 1 grammar finding(s): ears:non-singular=1` —
and that single finding is on FR-031 line 56, outside this review's scope. Every
finding below therefore comes from reading, not from the engine: three
ambiguities that change what gets built, a family of compound `SHALL … and
SHALL …` bullets the engine does not flag, and several restrictions whose
violating case has no stated response.

## Findings

| ID | Severity | Summary | Refs |
|---|---|---|---|
| FND-520 | high | A dialect the caller names badly has two incompatible responses and no rule choosing between them. FR-045 says `If a caller names a dialect outside that vocabulary, then selectFrontend SHALL throw a usage error`, while FR-045 also says `No frontend SHALL throw for an input defect; an input defect is a diagnostic`, and FR-052 says `If the caller names an unknown command or flag, then the CLI SHALL print the usage text` with exit `2`. Nothing states what `compile --dialect json-schema` does: throw and exit `2`, or emit a blocking diagnostic and exit `1`. Add to FR-052 `If --dialect names a value outside the frontendDialect vocabulary, then compile SHALL print the usage text and exit 2`, and restrict FR-045's throw statement to `a programming error raised to a caller inside the process, not to a CLI user`. | FR-045, FR-052 |
| FND-521 | high | FR-049 truncates against an unordered list. `If the number of diagnostics reaches maxDiagnostics, then the compiler SHALL truncate the list to that many` and `The compiler SHALL stop analysing once that limit is reached` together make the surviving set a function of analysis order, while `sortDiagnostics SHALL order by locus.path, then …` applies only afterwards. Two implementations that analyse in different orders both satisfy the requirement and emit different bytes, which contradicts NFR-019's `byte-identical … output for identical inputs`. State the order: `The compiler SHALL analyse in a declared deterministic order, and when the diagnostic count reaches maxDiagnostics SHALL truncate the list in that analysis order and append one agent-ix.compiler.DIAGNOSTIC_LIMIT_REACHED`, and say that sorting is applied to the truncated list. | FR-049, NFR-019 |
| FND-522 | high | FR-050's cross-field obligation names roughly fifteen rules in one `SHALL enforce` bullet — `multiplicity bounds, collection-only ordered/unique flags, presence derived from lower, unit only on a typeRef that resolves … , constraint applicability …, a compiling pattern regex, relationship targets resolving …, acyclic composite relationship graphs, clauseId unique per type, pre/post bound to a declared clauseId, operation parameter names unique, relationships/operations only on record, and identity uniqueness` — and names no diagnostic code for any of them. FR-046, FR-047, FR-048, FR-051, and FR-052 name a code for every unwanted case; FR-049-CON-3 requires the registry's code set to equal the emitted set, and that set cannot be computed from FR-050 as written. Split into one `If <rule violated>, then readContractIr SHALL raise <code> at <locus>` statement per rule, or add a closed rule→code table. | FR-050, FR-049 |
| FND-523 | medium | FR-047's export/capability bullet elides the second obligation's verb and locus: `If an import names an export the imported manifest does not declare, then the compiler SHALL raise agent-ix.compiler.IMPORT_EXPORT_MISSING at the naming entry's locus; if it names a capability no resolved profile of that package declares, then agent-ix.compiler.IMPORT_CAPABILITY_MISSING`. The second half has no `SHALL raise` and no stated locus. Split it: `If an import names a capability no resolved profile of the imported package declares, then the compiler SHALL raise agent-ix.compiler.IMPORT_CAPABILITY_MISSING at the naming entry's locus`. | FR-047 |
| FND-524 | medium | FR-046 sets `source.digest` to `the SHA-256 of the package's source bytes under the canonicalization of FR-048`, but FR-048 defines no "source bytes" digest — it defines `contentDigest` as `the SHA-256 of the canonical byte form of that package's path-sorted source file list, each entry being its package-root-relative /-separated path and its bytes`. Two readers would emit different `source.digest` values (concatenated bytes versus the path-sorted list form), and the value is compared byte-for-byte downstream. Restate as `source.digest SHALL equal the root package's contentDigest as defined by FR-048`, or define the second digest explicitly in FR-048. | FR-046, FR-048 |
| FND-525 | medium | FR-051's evolution statements are written only for the cross-version case: `readIrAsContract(document, "1.0.0") SHALL return the 1.0.0 projection of a 1.1.0 document` and the mirror for `1.1.0`. No statement covers projecting a document to the version it already declares, nor a `targetVersion` outside `{1.0.0, 1.1.0}`, and FR-051-AC-9's round-trip depends on the identity case. Add `Where the document's contractVersion equals targetVersion, readIrAsContract SHALL return the document unchanged with loss empty` and `If targetVersion is not a published contract version, then readIrAsContract SHALL raise agent-ix.compiler.UNSUPPORTED_CONTRACT_VERSION`. | FR-051 |
| FND-526 | medium | FR-051 binds the IR evolution rules to a document rather than to the system: `The published policy SHALL state that within contract major version 1 a revision may add optional members and may widen a closed vocabulary, SHALL NOT remove or retype a member, SHALL NOT narrow a vocabulary, and SHALL be discriminated by contractVersion in one schema file`. The three inner prohibitions are quoted content of a document; no statement obliges the compiler, the schema, or the branch to obey them, so a revision that removes a member violates no requirement. Keep the documentation obligation as one statement and add the enforcing statement separately: `If a revision removes or retypes an IR member, or narrows a closed vocabulary, then the diff SHALL classify it breaking` (FR-051 already carries the matching rows in its classification table — the policy statement should reference them rather than restate them). | FR-051 |
| FND-527 | medium | FR-050 states an agreement, not a behaviour: `The compiler's reader SHALL agree with the issue #34 test-scoped reader and the Python reader on the diagnostic codes produced for every case in fixtures/semantic/v1/negative/reader-cases.json`. It names three subjects, names no authority when they disagree, and states no response. It belongs in Verification, or should be restated as an obligation on one subject: `For every case in reader-cases.json, the compiler's reader SHALL produce the diagnostic codes the case declares as expected`, with the three-way comparison left to FR-050-AC-3. | FR-050 |
| FND-528 | medium | Fourteen Behavior bullets carry two or more `SHALL` and are not flagged by the engine: FR-046 `@role … SHALL be repeatable; every other decorator SHALL be single-valued and a second application SHALL raise …` (three), the `UNSUPPORTED_SCALAR_BASE` bullet (`SHALL raise … and SHALL NOT substitute`), the `@collection`, `@multiplicity`, `@defaultKind`, `@unit`, constraint-lowering, and `origin` bullets, plus FR-051's disposition-ranking bullet (`SHALL rank … SHALL set aggregateDisposition … and each entry's disposition …`), its absent-input bullet, its idempotence bullet, and FR-052's `compile SHALL resolve the package graph, verify or build the lock, run the selected frontend, validate the emitted document, and write the IR to --out only when no diagnostic is blocking` (five ordered actions in one statement). Each should be split into one statement per obligation so each maps to one acceptance criterion. | FR-046, FR-051, FR-052 |
| FND-529 | medium | NFR-020's Statement packs three obligations under one subject — `SHALL treat every manifest … as untrusted data, SHALL terminate within declared finite limits on any input, and SHALL neither execute input, reach the network, escape the declared roots, nor write outside a caller-named output path` — and states no response for a limit that is exceeded; only NFR-020-AC-1 says it is `a distinct blocking diagnostic naming the limit and its value`. Split into three statements and lift the response into the second: `If an input exceeds a declared limit, then the compiler SHALL terminate with a blocking diagnostic naming the limit and its value`. | NFR-020 |
| FND-530 | medium | FR-052's exit-code statement is three obligations and leaves one case open: `Every command SHALL exit 0 on success, 1 when the work produced a blocking diagnostic or a breaking aggregate, and 2 on a usage error`. "Success" is not defined for a run that produced only non-blocking diagnostics; FR-049-AC-9 settles it (`a non-blocking diagnostic writes the file and exits zero`) but no SHALL does. State it: `A command whose diagnostics are all non-blocking SHALL exit 0`, then the blocking and usage cases as separate statements. | FR-052, FR-049 |
| FND-531 | low | Two Descriptions carry two SHALLs each: FR-050 (`SHALL validate every IR document … and SHALL define one normalized serialization and fingerprint`) and FR-051 (`SHALL classify the difference … and SHALL define and implement the policy`). Both are atomized in Behavior, so traceability holds; reduce each Description to one summary SHALL. FR-048's Description additionally carries the meta-sentence `The two obligations are stated separately under Behavior`, which is editorial guidance rather than a requirement statement. | FR-048, FR-050, FR-051 |
| FND-532 | low | Passive or object-subject statements whose actor is not named: FR-047 `A recursive type graph within one package SHALL NOT be treated as a package cycle` (treated by whom), FR-049 `A diagnostic's locus.path SHALL be relative to the package root` and `A diagnostic message SHALL NOT contain an absolute path, a timestamp, a hostname, or a duration` (emitted by whom), FR-045-CON-2 `A FrontendResult SHALL carry ir: null whenever …`, FR-048-CON-1 `The fingerprint SHALL change for every change to an included input`, FR-051 `Each projection SHALL validate against the published schema`. Name the emitting actor — the frontend, the `diagnostic` constructor, `canonicalize`, `readIrAsContract`. | FR-045, FR-047, FR-048, FR-049, FR-051 |
| FND-533 | low | NFR-021's Statement subject is `The compiler core`, but the obligation `SHALL land without publishing a package, changing a published contract, changing a downstream consumer, or altering the frozen prototype path` is a process obligation on the delivery, and its own Scope says `Applies to: the whole branch`. Restate the subject as `The branch delivering the compiler core SHALL land without …` so the subject matches the scope and the four verification methods. | NFR-021 |
| FND-534 | low | NFR-019's Statement ends with an unassigned alternative: `with every host-varying input — working directory, locale, clock, hostname, environment, file-system enumeration order, and search-path order — either supplied explicitly or excluded from the output`. Which of the seven is supplied and which is excluded is settled only by the Measurement table (all seven are excluded from the output; the search path is supplied). State the disposition per input, or drop the alternative and say `excluded from the output, except the search path and the package root, which SHALL be supplied explicitly`. | NFR-019 |
| FND-535 | low | FR-052 `The CLI SHALL create no directory outside the parent of a path the caller named` states only a prohibition; whether the CLI creates that parent when it is absent, or reports a diagnostic, is unstated, and NFR-020-AC-6 asserts only that it `writes only the paths the caller named`. Add the positive case: `If the parent directory of a caller-named output path does not exist, then the CLI SHALL <create it | raise agent-ix.compiler.OUTPUT_PATH_UNAVAILABLE>`. | FR-052, NFR-020 |
| FND-536 | low | FR-051's classification table packs several distinct changes and dispositions into single rows — `Multiplicity widened; multiplicity narrowed; ordered or unique flipped` → `additive; breaking; breaking`, and likewise the relationship, operation, clause, constraint-keyword, and kernel-scalar rows. The pairing is positional and a reader must count to align them. Give each observed change its own row so each maps to one fixture case in `compatibility/cases.json`. | FR-051 |
