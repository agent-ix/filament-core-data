# [US-019] Reach every generated target through one seam

## Story

**As a** consumer generating native types from a semantic contract
**I want** every target this repository implements to answer through the one
documented generation entry point
**So that** I can select a target by name without discovering that some targets
are delivered by a published seam and others only by a private development
command I was never told about.

## Context

[US-011](./US-011-consume-semantic-contracts-in-rust.md) established the Rust
consumer's need and the backend that serves it. That backend exists: it emits a
complete crate, it has four golden crates, mutation and property batteries, and
its own diagnostic register, and it runs today through `make rust-*`.

It is not reachable. The generation seam registers `rust` as a declared target
with no implementation, so a caller asking the documented entry point for a Rust
package receives `state: "unavailable"` and a diagnostic naming the ticket that
supposedly still owes the work. The capability is built and unplugged, and the
refusal is not merely unhelpful — it is false. A consumer who believes it goes
looking for a backend that is already written.

The gap is an interface mismatch, not missing capability. The seam requires an
object carrying an identity, a version, the contract versions it accepts, the
features it claims and one `generate` call; the backend exposes a function that
takes a request and a writing sink. The emitting half is already pure, so
nothing about what is generated has to change for the two shapes to meet.

A private command is a reasonable thing for a backend author to keep. It is not
a reasonable thing for a *consumer* to have to find. The distinction this story
draws is between a development convenience and a delivery path: both may exist,
but only one is the contract, and a target that is delivered only by the former
is not delivered.

Two things follow that are easy to miss. A request document names the backend
that will answer it, and that name is rendered into the generated package as its
generator identity — so a caller that selects a target but sends some other
backend's descriptor produces a package that misattributes its own origin. And a
seam that has only ever routed to one backend has never had its selection
exercised: the arm is present but unmeasured until a second backend registers.

## Acceptance Examples (Illustrative)

### US-019-EX-1: The documented entry point generates a Rust crate

- **Given** a semantic IR document the Rust backend accepts
- **When** the consumer asks the generation seam for the `rust` target
- **Then** a crate is generated and the result carries the Rust backend's own
  identity, rather than an `unavailable` refusal naming a ticket

### US-019-EX-2: The seam and the private command agree byte for byte

- **Given** one semantic IR document
- **When** it is generated once through the seam and once through the backend's
  own development command
- **Then** every emitted file is byte-identical between the two, so the seam is
  a route to the backend and not a second implementation of it

### US-019-EX-3: A generated package names the backend that made it

- **Given** a caller selecting the `rust` target
- **When** the generated crate records its generator identity
- **Then** it names the Rust backend, and a package generated for one target
  never carries another backend's identity

### US-019-EX-4: An unimplemented target still refuses by name

- **Given** a target the contract declares and this repository has not built
- **When** the consumer asks the seam for it
- **Then** it is refused as unavailable with the owning ticket named, because
  registering one backend must not turn an honest refusal into a crash or a
  silent empty success

## Options (Exploratory)

Approaches considered while scoping, none implying commitment: moving the
backend's own writing entry point behind the seam and deleting the development
command; reshaping the seam to accept either interface; or adapting the backend
to the seam's shape and leaving the development command in place. The first
removes a working development path for no consumer benefit and enlarges a change
that is otherwise additive. The second makes the seam's contract negotiable,
which is the property that makes it worth having.

## Constraints (Contextual)

The generated bytes are not open for renegotiation here: this story is about
reachability, and a change that altered what the Rust backend emits would be a
different change with a different blast radius. The seam performs no file
writing, so nothing here moves the filesystem boundary. Registering a backend is
not evidence that the target is complete, published, or cross-language
agreed — those are separate gates and this story satisfies none of them.

## Dependencies (Contextual)

Relationships observed while scoping. Upstream: the generation seam and its
target registry, and the Rust backend's own emitting half. Downstream: any
consumer selecting a target by name, and the cross-language agreement gate that
cannot compare targets it cannot reach. These are potential relationships, not
formal traceability.

## Priority and Risk (Informative)

Business value is high and urgency is high: the work being unreachable is the
whole of the defect, and the change is small relative to what it delivers. The
risk if unmet is that a finished backend continues to read as unfinished, and
that effort is spent rebuilding a capability the repository already has.

## Notes (Informative)

Open questions captured for later analysis, introducing no requirement: whether
the two backends' feature vocabularies should be reconciled, since they name the
same concepts with different spellings; and whether the seam's manifest and the
backend's own manifest, which share a field name with different meanings, should
be resolved to one.
