# [FR-082] Lower the kernel JSON Schema bundle to semantic IR v1.1

## Description

The compiler SHALL lower the thirty JSON Schema 2020-12 documents [FR-081](./FR-081-declare-the-semantic-kernel-bundle.md)
enumerates into one semantic IR document at `contractVersion` `1.1.0`, through a
new frontend registered on the seam of `src/compiler/frontend/seam.mjs`, so that
the four kernel targets are generated from a single validated IR document rather
than each reading the schema bundle in its own way and disagreeing about what it
said.

The lowering is closed by construction. It recognises exactly the JSON Schema
keywords the kernel bundle actually uses, and a keyword outside that set is a
diagnostic — never a silent drop. A lowering that ignores what it does not
understand produces an IR document that is smaller than its input and says so
nowhere, and every downstream package inherits the omission as though it were
the contract.

## Inputs

- The thirty documents enumerated by `packages/semantic-kernel/bundle.json` under `packages/semantic-core/generated/json-schema/`, read through the injected host
- The kernel package identity `agent-ix/semantic-core` at version `0.2.0`, the schema base `https://schemas.agent-ix.org/semantic-core/0.2.0/`, and `kernelDigest()` — all supplied by `scripts/build-semantic-kernel.mjs` from `packages/semantic-kernel/bundle.json`
- `packages/semantic-core/kernel-scalars.json`, whose `JsonObject` row prescribes the lowering `kind: record, fields: [], unknownPolicy: preserve`
- `schema/semantic/v1/semantic-ir.schema.json` and `schema/semantic/v1/common.schema.json`
- The FR-050 reader `readContractIr` and schema validator `validateIrDocument`
- The injected host of NFR-019 and NFR-020, through which every read is made

## Outputs

- `src/compiler/frontend/json-schema/frontend.mjs`, exporting `dialect`, `sourceForm`, and `run(request)`, matching the `FrontendResult` shape `src/compiler/frontend/typespec/frontend.mjs` returns
- `src/compiler/frontend/json-schema/lower.mjs`, the pure lowering
- `src/compiler/frontend/json-schema/keywords.mjs`, the closed recognised-keyword set
- A `.d.mts` declaration beside every added `.mjs` in this frontend's directory, as the TypeSpec frontend does for its own modules
- A registration on the `typespec` entry of the registry in `src/compiler/frontend/seam.mjs`, under the source form `json-schema-bundle`
- `packages/semantic-kernel/semantic-ir.json`, the kernel IR document, fifty-three type definitions lowered from the thirty documents, written by `scripts/build-semantic-kernel.mjs`
- Diagnostics `agent-ix.compiler.UNSUPPORTED_SCHEMA_KEYWORD` and `agent-ix.compiler.UNSUPPORTED_SCHEMA_SHAPE`, added as members of `DIAGNOSTIC_CODES` in `src/compiler/diagnostics.mjs`
- The `src/compiler/inventory.json` component record for every module this requirement adds, and `docs/semantic-data-system/compiler-diagnostics.md` regenerated by `scripts/build-compiler-docs.mjs` as a consequence of the two added codes
- Cases in `test/semantic-kernel.test.ts`

## Behavior

### The closed keyword set

- `keywords.mjs` SHALL declare the recognised keyword set as exactly: `$schema`, `$id`, `$ref`, `type`, `properties`, `required`, `unevaluatedProperties`, `not`, `description`, `const`, `enum`, `anyOf`, `items`, `minItems`, `pattern`, `minLength`, `minimum`, and `maximum`.
- That set is the measured keyword usage of the committed bundle and nothing wider. Widening it to the keywords JSON Schema 2020-12 defines would make the lowering silently accept constructs no kernel document contains and no target has been proven to render.
- If a member name appears in a lowered subschema and is not in the recognised set, then the lowering SHALL emit one blocking `agent-ix.compiler.UNSUPPORTED_SCHEMA_KEYWORD` diagnostic naming the keyword and the JSON Pointer at which it occurred, and SHALL return no IR document.
- The lowering SHALL NOT drop, ignore, or best-effort an unrecognised keyword under any flag, option, or environment setting. There is no permissive mode.
- If a recognised keyword occurs in a position the kind-assignment table below does not cover, then the lowering SHALL emit one blocking `agent-ix.compiler.UNSUPPORTED_SCHEMA_SHAPE` diagnostic naming the pointer and the shape, distinguishing "this repository has never seen this arrangement" from "this keyword is outside the set", because the two send a reader to different files.
- `unevaluatedProperties` SHALL be recognised only in the exact form `{"not": {}}`, which is what `seal-object-schemas: true` in `packages/semantic-core/tspconfig.yaml` makes the emitter write; any other value of `unevaluatedProperties` SHALL raise `UNSUPPORTED_SCHEMA_SHAPE`.

### Kind assignment

- The lowering SHALL assign an IR `kind` by this table and by no other rule:

| Schema shape | IR result |
|---|---|
| `type: "string"` with `pattern` or `minLength` | `kind: "scalar"`, `scalar: "string"`, one `pattern` or `minLength` constraint per keyword |
| `type: "string"` with `enum` | `kind: "enum"`, one `variants[]` member per enum member, in the order the document lists them |
| `type: "object"` with `properties` | `kind: "record"`, one `fields[]` member per property |
| top-level `anyOf` of `$ref`s | `kind: "union"`, one `variants[]` member per branch, named for its target and carrying `payloadType` equal to that target's identity |
| property-position `anyOf` (anonymous) | a minted `union` type, referenced by the field's `typeRef` |
| property `{"type": "string", "const": X}` | a minted single-variant `enum` |
| property `{"type": "integer", "minimum": m, "maximum": n}` | a minted `scalar`/`integer` with `min` and `max` constraints |
| property `{"type": "array", "items": X, "minItems": k?}` | the field's `typeRef` is `X`; `multiplicity` is `{ lower: k ?? 0 }` with no `upper` |
| property `{}` (unconstrained) | a minted `record` with `fields: []` and `unknownPolicy: "preserve"` |

- A `type: "object"` document carrying `unevaluatedProperties: {"not": {}}` SHALL lower to `unknownPolicy: "reject"`, because a sealed object schema admits no member the schema did not evaluate, and `preserve` or `surface` would each let a generated package accept a document the schema refuses.
- A `type: "object"` document carrying no `unevaluatedProperties` SHALL raise `UNSUPPORTED_SCHEMA_SHAPE` rather than defaulting a policy, because the committed bundle seals every object schema and an unsealed one would mean the emitter configuration changed.
- The unconstrained-property row SHALL produce exactly the shape `packages/semantic-core/kernel-scalars.json` prescribes for `JsonObject`: `kind: "record"`, `fields: []`, `unknownPolicy: "preserve"`. This narrows "any JSON value" to "any JSON object": `DefaultDecl.value` is `unknown` in `main.tsp` and `{}` in `DefaultDecl.json`, and IR v1.1 has no any-type. That narrowing is a declared representability loss with a diagnostic and a register row against `agent-ix/filament-core-data#11`; it is not repaired by editing a published schema.
- An `anyOf` whose branches are not all `$ref`s and are not all in the recognised property-position forms SHALL raise `UNSUPPORTED_SCHEMA_SHAPE`.

### Fields, multiplicity and presence

- `field.typeRef` is a single `semanticIdentity` under `semantic-ir.schema.json#/$defs/field`. An anonymous construct in a property position therefore SHALL be minted as its own named type and referenced by identity; no field may carry an inline shape.
- Every `fields[]` member and every operation parameter of the emitted document SHALL carry `multiplicity`, which `semantic-ir.schema.json` requires of every field at `contractVersion` `1.1.0` and `readContractIr` enforces as `agent-ix.semantic-ir.MISSING_MULTIPLICITY`.
- `presence` SHALL be derived from `multiplicity.lower` by the single rule `required` exactly when `multiplicity.lower >= 1`, and SHALL never be stated independently of it. The FR-050 reader checks the same relation as `agent-ix.semantic-ir.PRESENCE_MULTIPLICITY_MISMATCH`, so a lowering that computed the two separately would be asserting a fact the reader is about to re-derive.
- A property named in the document's `required` array and not an array-typed property SHALL take `multiplicity` `{ lower: 1, upper: 1 }`; a property absent from `required` and not array-typed SHALL take `{ lower: 0, upper: 1 }`.
- An array-typed property SHALL take `multiplicity` `{ lower: minItems ?? 0 }` with no `upper`, whether or not it is named in `required`.
- The consequence SHALL be recorded rather than papered over: `OperationDecl.params` is listed in `OperationDecl.json`'s `required` and carries no `minItems`, so it lowers to `lower: 0` and its derived `presence` is `optional`. IR v1.1 cannot express "the member must be present and may be empty". This is the second declared representability loss, adjacent to FND-956 in `spec/reviews/21-rust-serde-backend/failure-domain.md`, and it carries a diagnostic, a register row, and an issue filed against the contract owner.
- The lowering SHALL NOT resolve the loss by writing `lower: 1` for a required array, because that would make the generated packages refuse an empty `params` array that every kernel document permits.

### The declared dialect

- The emitted document SHALL declare `source.dialect` of `typespec`.
- `semantic-ir.schema.json` admits exactly two dialect values at `contractVersion` `1.1.0`, `typespec` and `spec-bundle`, read from `common.schema.json#/$defs/frontendDialect`. There is no `json-schema` dialect value at `1.1.0`; the bare `https://json-schema.org/draft/2020-12/schema` constant the schema also names is bound by the same `allOf` to `contractVersion` `1.0.0`, the frozen prototype shape, which is not a contract IR document.
- `typespec` is correct rather than merely permitted: the authored source is `packages/semantic-core/main.tsp`, and the thirty documents are the pinned official `@typespec/json-schema` `1.15.0` emitter's deterministic projection of it, recorded in `packages/semantic-core/generated/toolchain.json` and gated byte-for-byte by `make semantic-core-check`. The bundle is the transport, not the source. This requirement states that reasoning in the emitted document's provenance rather than leaving a later reader to infer it from a dialect value that looks wrong.
- `source.identity` SHALL be the source identity of `packages/semantic-core/main.tsp`, `source.version` SHALL be `0.2.0`, and `source.digest` SHALL be `kernelDigest()`, so the document names the authored source and digests the exact bytes it was actually lowered from.
- This requirement SHALL file an issue against the contract owner asking whether a deterministic projection of an authored source deserves its own `frontendDialect` value, and SHALL record that issue by number in the emitted document's provenance and in this repository's contract-gap register.
- This requirement SHALL edit no file under `schema/semantic/v1/`. Adding a dialect value to a published schema to make one's own document validate is how a contract stops meaning anything.

### Determinism and ordering

- Every list the lowering emits — `types`, `fields`, `variants`, `constraints`, `extensions`, and the minted-type set — SHALL be ordered by identity, compared by Unicode code point, so two runs over the same bytes produce byte-identical output.
- Ordering SHALL NOT depend on directory enumeration order, on the order `readdirSync` returns names, or on the insertion order of any map; the document set comes from the [FR-081](./FR-081-declare-the-semantic-kernel-bundle.md) enumeration and is sorted before it is walked.
- The lowering SHALL validate its own output against `semantic-ir.schema.json` with `validateIrDocument` and SHALL run `readContractIr` over it, exactly as the `typespec` frontend does, and SHALL return `ir: null` when either reports a blocking diagnostic. A frontend that emits a document its own reader rejects puts an invalid artefact in front of all four generated packages.
- `packages/semantic-kernel/semantic-ir.json` SHALL be written in the FR-050 `normalizeIr` byte form, so that "the same kernel IR" is a byte comparison and `make semantic-kernel-check` can decide it without judgement.

### Purity and the injected host

- Every read the frontend and the lowering perform SHALL go through the injected host, reaching the file system through no other route — the rule [FR-063](./FR-063-declare-the-generation-backend-seam.md) states for every backend, applied here to the input side.
- No module under `src/compiler/frontend/json-schema/` SHALL read a clock, an environment variable, the current working directory, or a network socket, and none SHALL import `node:fs`, `node:net`, `node:https`, or `node:child_process`.
- The lowering SHALL be a pure function of the bytes it is given and SHALL start no process.
- The frontend SHALL NOT throw for any defect in a lowered document; a defect in a compiled input is a diagnostic, and only a defect in the calling program is an exception, which is the rule `src/compiler/frontend/seam.mjs` already states.
- The frontend SHALL bound its work by the injected `limits`, raising the corresponding limit diagnostic on a document exceeding `maxNodes`, `maxDepth`, or `maxCollectionItems`, and SHALL terminate on a cyclic `$ref` chain rather than recursing without bound.
- This requirement SHALL add every diagnostic code it introduces as a member of `DIAGNOSTIC_CODES` in `src/compiler/diagnostics.mjs`, and no call site SHALL spell a diagnostic code as a string literal.
- The lowering SHALL NOT be reached through a new command-line verb. `src/compiler/cli.mjs` is byte-unchanged by this requirement, and `scripts/build-semantic-kernel.mjs` is the sole file-system boundary: it reads the thirty documents, calls the pure lowering, and writes `packages/semantic-kernel/semantic-ir.json`. That is the split `src/compiler/backends/rust-serde/index.mjs` already uses — one module writes, everything else is a pure function from a request to bytes — and it is why every purity rule above can be checked by grep over a directory rather than by review.

### Registration on the frontend seam

- The seam SHALL register this frontend on the `typespec` entry of its registry as the source form `json-schema-bundle`, alongside the [FR-046](./FR-046-lower-typespec-to-contract-ir.md) frontend as the source form `typespec-source`.
- The registration SHALL be a second form under one dialect rather than a sixth dialect key, because `FRONTEND_DIALECTS` is read from the published `common.schema.json` and is closed at `typespec` and `spec-bundle`; adding a registry key outside that vocabulary would make `selectFrontend` accept a value the contract does not define, and both frontends legitimately stamp `typespec` for the reason recorded above.
- `selectFrontend(dialect)` SHALL keep its present signature and SHALL keep throwing a `TypeError` for a dialect outside the published vocabulary.
- The seam SHALL expose `selectFrontendForm(dialect, form)`, returning the registered frontend for that form, and SHALL throw a `TypeError` naming the value and the forms the dialect registers when the form is unknown — a form outside the registry is the calling program naming something that does not exist, which no compiled input can cause.
- `runFrontend(request)` SHALL select the form from `request.sourceForm`, defaulting to the dialect's declared default form, so that every existing caller of `runFrontend` is unchanged by this registration.
- Each registered frontend SHALL stamp its own dialect and SHALL NOT read the dialect or form used to select it, preserving the seam's existing rule that no frontend can be made to claim another's identity.
- The seam SHALL apply `assertFrontendContract` to this frontend's result unchanged: a blocking diagnostic and a non-null document never come back together.
